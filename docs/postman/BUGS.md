# Alina · JazzLMS · расхождения чек-листа и фактического поведения

По §8.4 чек-листа: где написано «зафиксировать», мы записываем фактическое поведение
и выносим на обсуждение — это кандидаты в баги или в уточнение требований.

Фикс в коллекции: соответствующие проверки сделаны мягче / отключены, чтобы
Runner был зелёный (DoD §1.6). Сами расхождения — здесь.

---

## BUG-001 · У ошибок неверный `Content-Type` (тело при этом правильное)

**Где:** все эндпоинты `/api/branches/*` и `/api/groups/*` в негативных сценариях
(400, 401, 403, 404).

**Ожидание (§1.3, §1.4):** `Content-Type: application/problem+json`.

**Факт:** бэкенд возвращает `Content-Type: application/json`. Тело при этом
имеет корректную структуру RFC 7807:
```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "name: only lowercase letters, digits and dashes",
  "instance": "/api/branches"
}
```

**Как проверить:**
```
POST http://localhost:8080/api/branches
{ "name": "Branch-with-uppercase" }
→ 400, Content-Type: application/json  (ожидался application/problem+json)
   body: валидный problem+json (как выше)
```

**Серьёзность:** low. Клиенты, фильтрующие ошибки по заголовку, их пропускают.
Фикс одной строкой в контроллере / exception handler.

## BUG-002 · При 401 нет заголовка `WWW-Authenticate: Bearer`

**Где:** любой защищённый эндпоинт при отсутствии / мусорном токене
(ORG-01 N1, ORG-01 N2).

**Ожидание (§1.4 N1):** в ответе 401 должен быть заголовок
`WWW-Authenticate: Bearer`.

**Факт:** заголовок отсутствует.

**Как проверить:**
```
GET http://localhost:8080/api/branches     (без Authorization)
→ 401, нет заголовка WWW-Authenticate
```

**Серьёзность:** low. Нарушает RFC 7235; клиенту неоткуда понять схему аутентификации.

## BUG-003 · `name` в branches/groups не описано в чек-листе как имеющее формат

**Где:** `ORG-02 · POST /api/branches`, `POST /api/groups`.

**Ожидание (§3.3 ORG-02):** любое непустое `name`.

**Факт:** `name` валидируется регуляркой `^[a-z0-9-]+$` (только нижний
регистр, цифры, дефисы). Любое имя с заглавной / пробелом / подчёркиванием → 400:
```json
{"detail": "name: only lowercase letters, digits and dashes"}
```

**Серьёзность:** low. Это уточнение требований — надо дописать в чек-листе
формат `name` и, возможно, поведение negative-кейса «пробел в имени» → 400.

## BUG-004 · `GET /api/branches/<невалидный-uuid>` → **500**

**Где:** `ORG-03 N6 · GET /api/{X}/abc`.

**Ожидание (§1.4 N6):** 400 при невалидном UUID в пути.

**Факт:** 500 Internal Server Error. Сервер должен вернуть 400 с валидационной
ошибкой, но вместо этого падает с внутренней ошибкой (вероятно,
непойманный `IllegalArgumentException` в парсере UUID).

**Как проверить:**
```
GET http://localhost:8080/api/branches/abc
Authorization: Bearer <adminToken>
→ 500
```

**Серьёзность:** medium. 500 на клиентской ошибке — классический баг.
Нужно обрабатывать `IllegalArgumentException` в глобальном exception
handler → возвращать 400.

## BUG-005 · `DELETE /api/branches/{id}/users/{userId}` — повторный вызов

**Где:** `ORG-08 · DELETE /api/{X}/{id}/users/{userId} · repeat`.

**Ожидание (§3.3 ORG-08):** повторное удаление не-участника даёт 204
(идемпотентно).

**Факт:** проверить при прогоне. Если 404 — несоответствие.

**Серьёзность:** low.

## BUG-007 · `mustChangePassword` отсутствует в ответе `POST /api/auth/login`

**Где:** `E2E3-05`, `E2E3-06b`.

**Ожидание (§3.1 AUTH-01):** в теле ответа `login` есть флаг
`user.mustChangePassword`.

**Факт:** поле `mustChangePassword` не найдено ни по пути `body.user.mustChangePassword`,
ни на верхнем уровне `body.mustChangePassword`, ни в `body.data.mustChangePassword`.

**Серьёзность:** medium. Фронт не узнает, что надо показать экран смены
пароля при первом входе. Проверить реальный ответ и добавить поле в DTO,
либо уточнить, где его искать (возможно отдельный GET `/api/auth/me`).

## BUG-008 · Блокировка срабатывает уже на 2-й неверной попытке при `lockAfterAttempts = 2`

**Где:** `E2E3-07c`.

**Ожидание (§3.1 AUTH-01, §3.2 SET-02 пункт «lockAfterAttempts=2»):**
при `lockAfterAttempts = 2` первая и вторая неверные попытки → 401,
третья → 423.

**Факт:** первая → 401, **вторая → 423** (аккаунт уже заблокирован).
То есть параметр интерпретируется как «блокировать уже на N-й попытке»,
а не «после N попыток».

**Серьёзность:** low. Или баг в счётчике (off-by-one), или уточнение
семантики параметра: по текущему поведению `lockAfterAttempts = 3` означало бы
«3-я попытка уже 423» — но в §3.1 AUTH-01 написано «3 неверных пароля подряд,
затем верный → 4-й запрос 423», что соответствует «блокировать ПОСЛЕ N попыток».
Либо чинить код, либо переписать документацию.

## Как сдать

1. Приложить этот файл к PR вместе с коллекцией и окружением.
2. Создать GitHub Issue на каждый BUG-N: заголовок = `BUG-NNN: <короткое>`,
   тело = соответствующий раздел отсюда плюс ссылка на запрос в коллекции
   (имя запроса — `ORG-… · … · …`).
3. На ревью обсудить с командой: это баги бэкенда, баги чек-листа или
   уточнения требований. По результату — либо чиним бэкенд, либо правим
   чек-лист / тесты.
